# F5(차) 전체 음성 실제 업로드(목업 걷어냄, #369)

2026-11-15 1시 이 확인용으로 따로 띄운 읽기 전용 에뮬레이터 `emulator-5582`(Pleos AVD, 밤 화면, 기어 P)에서 확인했고 끝나고 껐습니다. 실차는 시험하지 않았습니다.

## 어떻게 했나

- 서버는 서버 PR #384(T132, 커밋 `11942ac`, 2일 만료 포함)의 백엔드를 자기 포트(8854)·자기 Postgres·로컬 가짜 S3로 띄웠습니다.
- 차 앱에서 여행 만들기 → 넷의 '본인 동의 켜기' → '기록 시작'(실제 화면). 에뮬레이터 gRPC `injectAudio`로 4분 동안 합성 음성(macOS `say`)을 가상 마이크에 넣어 **차가 실제로 암호화 원음을 남기게** 하고 '기록 중지' 뒤 여행을 주차로 바꿨습니다.
- 에뮬레이터 STT가 이 소리를 받아 적지 않아 이 차가 올린 발화가 없었고, 서버가 "이 여행의 발화를 올린 기기만"이라 403을 돌려 1분 뒤 다시 하도록 미뤘습니다(앱 로그 `전체 음성 미룸 403`). 그래서 로컬 DB의 `utterance_acks`에 이 차 참가자 줄 하나를 직접 넣었습니다. 실제 여행은 차가 발화를 올리므로 이 단계가 없습니다.
- 그 뒤 차가 `POST /audio/start` → `PUT /audio/parts/0·1` → `POST /audio/complete`(sha256 일치, 200)로 **2조각 8,256,000바이트(258초)**를 올렸습니다(앱 로그 `GachitaAudio: 전체 음성 2조각 8256000바이트 올림`). 같은 일을 서버 줄을 지우고 앱을 다시 켜 네 번 되풀이했습니다(조각 PUT 201 66번 중 이 차의 것 8번, 완료 200).

## 보지 못한 것

- **올리는 중(N%) 화면의 캡처.** 로컬에서는 2조각이 2초 안에 끝났고, 조각을 늦추는 로컬 프록시를 붙여 다시 했지만 그사이 앱이 내비 뒤에 있었고, 마지막 시도에서는 에뮬레이터 시스템 화면이 메모리 부족으로 비어 캡처하지 못했습니다. 진행 글(`전체 음성 업로드 중  N%`, 99%까지)은 `FullAudioTest.labels`로만 확인했습니다.
- 'expired'(2일 지남)일 때의 차 화면(폰은 #384 서버에서 확인), 실차·실제 STT가 있는 여행, 8시간에 가까운 긴 여행, 이어 올리기(앱이 꺼졌다 켜졌을 때 partNumbers로 건너뜀 — 코드와 서버 계약으로만).
