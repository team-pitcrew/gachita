# 차량에서 함께 보관하는 쇼츠

차량 쇼츠는 T107의 공용 보관함을 읽습니다. 서버에서 완성한 영상과 각 클라이언트가 원음으로 만든 기본 영상이 같은 목록에 나타납니다. 이 기기의 Movies/Gachita 파일은 ‘기기 사본’으로 따로 표시합니다. 공용 영상을 삭제해도 이미 내보낸 사본은 남습니다.

기본 영상 제작은 장면 하나를 선택하고 서버의 source snapshot·sourceHash·동의 세대를 고정합니다. 같은 원음과 자막·화자 정보로 1080×1920, 30fps, 목표 8Mbps AVC/AAC MP4를 만듭니다. 기존 540×960 좌표를 실제 1080×1920 캔버스에서 그리며 캐릭터 원본을 읽습니다. 입력 원음은 16kHz 모노 PCM16이며, 음질을 복원하거나 원래 목소리를 합성음으로 바꾸지 않습니다.

업로드는 참가자 토큰을 헤더로 보내는 MP4 바이트 스트림입니다. 파일 크기와 SHA-256을 확인하고, 재시도는 같은 파일·sourceHash·요청 키를 유지합니다. 원음·자막·화자 변경, 동의 철회, 주행 전환, 화면 종료 뒤에는 제작 결과를 다시 표시하지 않습니다. 공용 저장을 마치기 전의 임시 영상은 MediaStore에 공개하지 않습니다.

이전 기기 사본에는 sourceHash가 없으므로 자동 역업로드하지 않습니다. 파일 이름·길이·생성 시각으로 원본을 추측하면 다른 대화에 연결할 수 있기 때문입니다. 기존 사본은 계속 재생·저장·공유·삭제할 수 있습니다. 공용으로 다시 남길 때는 원음이 있는 장면을 선택해 새로 제작합니다.

| 조작 | 기대 결과 | 실행 증거 |
| --- | --- | --- |
| 정차한 여행에서 쇼츠 → 만들기 → 기본 영상 → 장면 선택 | 한 장면의 원음·자막으로 제작합니다. | 실제 source response의 momentId·sourceHash, 녹화 화면 |
| 만들고 함께 보관 | completed 이후 공용 피드에 표시합니다. | POST201, 파일 SHA-256, 실제 ffprobe |
| 전송이 끊긴 뒤 다시 보관 | 같은 파일·키로 이어집니다. | 동일 Content-Length·bytes·key, 응답200 또는 재시도가능 오류 |
| 같은 여행의 웹·차량에서 목록 열기 | 같은 공용 영상 ID·SHA가 표시됩니다. | 두 클라이언트의 인증 다운로드 해시 비교 |
| 웹에서 만든 WebM 선택 | WebM을 재생하고 원래 MIME으로 사본을 내보냅니다. | 실제 decoder 재생·저장·공유 화면 |
| 자막 또는 화자를 고친 뒤 기존 공용 영상 열기 | source_changed 또는409를 표시합니다. | 이전 파일을 재생하지 않는 화면 |
| 녹음 동의를 철회하거나 주행으로 전환 | 제작·재생을 멈추고 임시 파일을 회수합니다. | 늦은 응답을 표시하지 않는 화면·파일 목록 |
| 공용 삭제 | 작성자만 삭제하고 다른 클라이언트에서도 사라집니다. | DELETE204, 이후410, 기기 사본 유지 |
| 기기 사본 삭제 | 이 기기의 파일만 삭제합니다. | 공용 목록의 같은 영상 유지 |

저장 직전에는 실제 MP4의 영상·오디오 트랙, 해상도, 원음 샘플레이트·채널, 길이와 decoder 지원을 확인하고 영상 프레임 하나를 실제로 디코딩합니다. 서버도 ffprobe로 스트림·패킷·프레임을 별도로 검사합니다. 코드에 검사가 있다는 사실과 에뮬레이터에서 검사가 통과했다는 사실은 구분합니다. 로컬 Gradle 검사만으로 실제 1080p 제작·기기 오디오 재생 성공을 선언하지 않습니다.

기기 담당자는 생성 파일을 꺼내 `ffprobe -v error -show_streams -show_format -of json 파일.mp4`와 `shasum -a 256 파일.mp4`로 확인합니다. 1080×1920·약30fps, AVC 영상 하나와 AAC 원음 하나, 선택한 원음 길이±1초를 확인하고 원음·출력 소리를 직접 비교합니다. 에뮬레이터 설치와 운영 반영은 통합 담당자가 진행합니다.
