# ADR-0018: Postgres 볼륨은 서버의 루트 디스크(local-path)에 두고, 서버를 갈 때는 S3 백업으로 잇는다

* **상태:** 제안, 2026-11-13
* **관련:** T28(#34), T52(#89, 다시 펼 때 복구), T57(#94, 지정 시점 복구), T62(#107, 복구 시간 실측), [ADR-0016](0016-slo-capacity-single-postgres.md) 2절(RPO 5분, RTO 30분), [ADR-0017](0017-alb-by-controller-and-fold-order.md)(접기 순서)

## 배경

- Postgres 볼륨(8 Gi)은 K3s의 local-path로 서버의 루트 디스크(EBS gp3 40 GB, 암호화)에 있다. 서버를 갈면 볼륨도 같이 사라진다. 그때는 S3의 전체 백업과 WAL로 다시 세운다(T52).
- T28은 이 볼륨을 EBS CSI 드라이버의 볼륨으로 옮겨, 서버를 갈아도 같은 디스크를 다시 붙일지를 묻는다.

## 서버를 잃는 경우마다 지금 일어나는 것

| 경우 | 디스크 | 되살아나는 길 | 데이터 |
|---|---|---|---|
| 파드·Postgres 재시작, 노드 재부팅 | 그대로 | CloudNativePG가 같은 볼륨으로 다시 띄움 | 그대로 |
| 하드웨어 장애 | 그대로 | EC2 자동 복구(`auto_recovery = default`)가 같은 인스턴스·같은 EBS로 옮김 | 그대로 |
| 계획한 접기 | 지워짐 | 길을 닫은 뒤 마지막 전체 백업 → 다시 펼 때 복구(ADR-0017, T52) | 잃지 않음(마지막 쓰기까지 백업에 들어감) |
| 서버를 새로 만들어야 하는 장애(디스크 손상, 첫 부팅 스크립트 변경) | 지워짐 | S3의 마지막 전체 백업과 WAL로 다시 세움 | 최대 5분치(WAL 보관 주기, RPO) |

실측(11/13, 실제 계정): 서버를 새로 만들어 복구로 펴기까지 17분 13초(세 번 16~18분), 같은 백업에서 Postgres만 다시 세우는 데 56~58초(T57의 복구 연습). 둘 다 RTO 30분 안이다.

## 검토한 선택

| | (가) 지금대로: 루트 디스크 + S3 복구 | (나) EBS CSI 볼륨을 남겨 다시 붙임 |
|---|---|---|
| 새 서버에서의 데이터 | 마지막 백업 + WAL(최대 5분 잃음) | 디스크 그대로(잃지 않음) |
| 더 생기는 것 | 없음 | 드라이버(컨트롤러와 노드 데몬셋, 메모리 약 200 MiB), 볼륨을 만들고 붙이는 IAM 권한(같이 쓰는 계정이라 태그 조건), 접어도 남는 볼륨과 그 가용 영역에 서버를 고정하는 일, 정적 PV를 CloudNativePG의 PVC에 묶는 절차 |
| 접기·펴기 | 그대로(ADR-0017) | 볼륨을 남는 묶음으로 옮기고, 펼 때 같은 영역에 서버를 띄워 붙임. 볼륨이 붙은 채 남으면 VPC 삭제는 막지 않지만 접기의 '남은 것' 검사가 볼륨을 따로 봐야 함 |
| 비용 | 0 | gp3 8 GiB 월 약 $0.73(접어도 남음) |
| 복구를 쓰는 횟수 | 펼 때마다 → 백업이 늘 검증됨 | 디스크를 붙이면 백업 복구는 장애 때만 쓰여 검증이 드묾 |

## 결정

**(가)를 유지한다. Postgres 볼륨은 루트 디스크의 local-path에 두고, 서버를 새로 만들 때는 S3 백업으로 잇는다. EBS CSI 드라이버는 넣지 않는다.**

- 디스크가 사라지는 경우는 계획한 접기와 서버를 새로 만들어야 하는 장애뿐이다. 앞의 것은 접기 순서(길을 닫은 뒤 백업)로 데이터를 잃지 않고, 뒤의 것은 ADR-0016이 정한 RPO 5분 안이다.
- 재부팅과 하드웨어 장애에서는 루트 EBS가 그대로 남는다. (나)가 더 지키는 것은 '새 서버를 만들어야 하는 장애에서의 5분치'뿐이다. 그 대가가 드라이버, IAM 권한, 가용 영역 고정, 접기 절차의 분기다.
- 펼 때마다 복구로 Postgres를 세우므로, 백업이 실제로 되살아나는지가 매번 확인된다(T52, T57).

## 다시 볼 때

- RPO 5분을 줄여야 할 때(SLO를 99.9%로 올리는 3단계, ADR-0016 4절). 그때는 볼륨보다 Postgres 대기 복제본이 먼저다.
- 데이터가 커져 복구가 30분에 가까워질 때. 볼륨 8 Gi가 차면 전체 백업 내려받기와 WAL 되감기가 길어진다. `infra.sh restore`(T57)의 '준비까지 걸린 시간'으로 본다.
- 워커를 붙여(2단계) Postgres를 서버 밖 노드로 옮길 때. 노드를 바꿔 옮겨 다니려면 노드에 묶인 local-path로는 안 된다.

## 결과

- 바뀌는 선언은 없다. `root_volume_gb`(40)와 `storage.size`(8Gi), local-path 그대로.
- 볼륨이 루트 디스크를 같이 쓰므로, ADR-0016의 '늘리는 신호'(디스크 70%)는 루트 디스크 전체에 대고 본다.
