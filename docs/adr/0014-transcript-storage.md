# ADR-0014: 전사본은 발화 한 줄씩 여행 DB에 두고, 고른 장면만 프로필로 옮긴다

* **상태:** 제안, 2026-11-13 (T48. PR 병합으로 정함. 구현하는 T39 담당과 기획 쪽의 확인이 필요)
* **관련:** T48(#80), T39(#62, PR #85), T12(#13, PR #55), T36, T38, T43, T45, [ADR-0008](0008-in-car-capture-and-sdk-stt.md), [ADR-0013](0013-network-edge-and-isolation.md), [ADR-0016](0016-slo-capacity-single-postgres.md)

## 배경

- 여행 대화는 차량 앱이 Pleos STT로 받아 적고, 발화 단위(시각, 글자, 좌석 구역)를 기록본으로 서버에 보냅니다. 기록본은 사람별 프로필에 묶어 저장합니다(ADR-0008). 48시간 뒤 무엇을 남길지는 T39에서 정하기로 했습니다.
- 지금 서버는 여행 하나를 `trips(code, doc jsonb)` 한 문서로 두고, 발화를 저장하는 길이 없습니다. 여행 읽기는 48시간으로 닫힙니다. 여행과 프로필은 저장소가 따로이고 API만 둘에 닿습니다. 처음에는 Postgres 둘이었고(ADR-0013의 5절), ADR-0016으로 한 Postgres의 데이터베이스 둘이 됐습니다. 이 문서의 '여행 DB'와 '프로필 DB'는 그 데이터베이스를 가리킵니다.
- 양은 작습니다. 11/13 에뮬레이터 실측에서 11분에 150문장이었습니다([ADR-0008](0008-in-car-capture-and-sdk-stt.md). 합성 음성이고 실차가 아님). 이 비율이면 3시간 여행이 약 2,500줄이고, 한 줄이 수백 바이트라 여행 하나가 1 MB에 못 미칩니다(어림).
- 차량의 통신은 끊깁니다. 보내는 쪽은 보관했다가 다시 보내고, 받는 쪽은 같은 것을 두 번 받아도 한 번만 남겨야 합니다(ADR-0013의 11절).
- 11/13에 음성 회의록 제품 셋의 클라이언트를 조사했습니다. 배포된 앱과 웹 꾸러미를 실행하지 않고 읽은 것(정적 분석)이라 서버가 어떻게 저장하는지는 보이지 않습니다.

| 제품 | 본 것 | 여기에 가져온 것 |
|---|---|---|
| Notion 7.42.3(데스크톱 앱 꾸러미의 기본 설정) | 실시간은 웹소켓 스트리밍 전사(1초마다 중간 결과), 중간 모델과 최종 모델이 따로 있음. 올린 파일은 배치 큐가 5분짜리 서명 주소로 받아 화자 분리까지 함. 15초 하트비트 | 먼저 받은 결과를 바로 저장하고 나중에 같은 줄을 고쳐 쓰는 2단. 큰 파일은 서명 주소로 직접 |
| 클로바노트(웹 꾸러미) | 노트 단위로 묶음. 녹음기가 `bufferIndex`를 올리며 보내고, 끝낼 때 `lastBufferIndex`를 알림. 인식 요청과 북마크는 별도 경로 | 순번을 붙여 보내고, 어디까지 받았는지를 주고받는 방식 |
| Fireflies(웹 꾸러미) | 실시간 전사의 한 줄이 문장, 화자 번호, 시작·끝 시각, 글자. 오디오는 주소로만 참조 | 발화 한 줄의 열 구성 |

셋 모두 전사는 시간순 문장 줄, 오디오는 따로 둔 파일, 요약과 북마크는 전사와 분리된 파생물이었습니다.

## 검토한 선택

**발화를 두는 곳과 모양**

| 선택 | 좋은 점 | 걸리는 점 |
|---|---|---|
| `trips.doc`에 배열로 | 표가 늘지 않음 | 발화가 올 때마다 문서 전체를 다시 씀. 동시에 쓰면 덮어씀. 문서가 계속 커짐 |
| S3에 여행별 파일 | 저장이 쌈 | 이어 붙이기, 중복 제거, 시간 범위 읽기를 직접 만들어야 함. 양이 작아 얻는 것이 없음 |
| **여행 DB의 표에 발화 한 줄씩** | 순번으로 중복을 걸러 냄. 시간 범위로 읽음. 후처리가 줄 단위로 고쳐 씀 | 표 하나와 지우는 작업 하나가 늘어남 |
| 처음부터 프로필 DB에 | 피드가 DB 하나만 읽음 | 여행 단위의 짧게 사는 데이터가 오래 두는 개인 저장소에 섞임. 프로필에 묶이기 전(화자 대조 전)의 발화를 둘 곳이 없음 |

**48시간 뒤 프로필에 남기는 방식**

| 선택 | 좋은 점 | 걸리는 점 |
|---|---|---|
| 여행 DB의 줄을 가리킴(참조) | 사본이 없음 | 여행 쪽을 지우면 끊어짐. 피드를 그릴 때마다 두 DB를 함께 읽음 |
| **고른 구간을 프로필 DB로 복사** | 여행 쪽을 지워도 남음. 48시간 뒤 피드는 프로필 DB만 읽음. 남긴 것이 무엇인지가 표 하나에 다 보임 | 같은 글자가 48시간 동안 두 곳에 있음 |

## 결정

**발화는 여행 DB의 `utterances` 표에 한 줄씩 받아 48시간만 두고, 사람이 고른 장면만 프로필 DB의 `moments`로 복사해 남깁니다.** 원음 전체는 지금처럼 차 밖으로 보내지 않습니다(ADR-0008).

### 1. 발화 표(여행 DB)

```sql
CREATE TABLE IF NOT EXISTS utterances (
  trip_code   text NOT NULL REFERENCES trips(code) ON DELETE CASCADE,
  device_id   text NOT NULL,             -- 보낸 차량 앱(설치 단위)
  seq         bigint NOT NULL,           -- 그 기기가 1부터 매기는 순번. 다시 보내도 같은 값
  started_at  timestamptz NOT NULL,
  ended_at    timestamptz NOT NULL,
  text        text NOT NULL,
  seat_zone   smallint,                  -- 좌석 구역. 모르면 NULL
  profile_id  uuid,                      -- 화자 대조 결과. 프로필 DB의 id(다른 DB라 외래 키 없음)
  confidence  real,                      -- STT가 주면 넣음
  audio_ref   jsonb,                     -- { key, start_ms, end_ms } 클립을 올렸을 때만
  geo         jsonb,                     -- { lat, lng } 없을 수 있음
  revision    integer NOT NULL DEFAULT 0, -- 후처리가 고쳐 쓴 횟수
  received_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (trip_code, device_id, seq)
);
CREATE INDEX IF NOT EXISTS utterances_time ON utterances (trip_code, started_at);
```

열은 T39의 할 일에 적힌 것(시각, 글자, 좌석 구역, 프로필, 확신도, 원음 구간, 위치)입니다.

### 2. 받기

```
POST /api/trips/:code/utterances
{ "device_id": "…", "items": [ { "seq": 41, "started_at": "…", "ended_at": "…", "text": "…", "seat_zone": 0 } ] }
→ 200 { "acked_seq": 41 }
```

- 차량 앱이 발화를 묶어 보냅니다. 같은 `(여행, 기기, 순번)`은 한 번만 남습니다(`ON CONFLICT DO NOTHING`). 순서가 어긋나 와도 받습니다.
- 서버는 1부터 빠짐없이 받은 마지막 순번(`acked_seq`)을 돌려줍니다. 차량 앱은 그 뒤의 것을 다시 보냅니다. 통신이 끊기거나 서버와 DB가 잠깐 멈춰도 잃지 않습니다.
- 차량 앱은 확인받은 발화도 여행 보관 기간(48시간) 동안 지우지 않습니다. 같은 동의 세대 안에서 서버가 돌려준 순번이 차량의 확인 순번보다 작으면(DB를 백업에서 되살려 최대 5분 치를 잃은 경우, ADR-0016의 RPO) 확인 순번을 그 값으로 내리고 그 뒤부터 다시 보냅니다. 동의 세대가 바뀌었으면 옛 세대 발화의 내용은 지우고, 그 순번만 `{seq, generation}`으로 보내 확인받습니다(T12·T39) — 순번을 빼면 확인 순번이 그 앞에서 멈춥니다. 이 동작은 차량 앱이 서버로 올리기 시작할 때(T36의 올리기, 지금은 보관만) 넣습니다.
- 한 번에 받는 크기를 작게 막습니다(예: 100줄, 256 KB). 값은 T39에서 정합니다.

### 3. 읽기

- 기록본은 시간순으로 읽고, 받은 데까지의 위치(커서)를 주어 이어 받습니다. 부탁과 도착 할 일은 지금처럼 여행 문서에서 같이 줍니다.
- 실시간으로 따라 읽는 화면이 필요하면 커서로 다시 묻는 것부터 시작합니다. 웹소켓이나 서버가 밀어 주는 방식은 그 주기로 모자랄 때 넣습니다.

### 4. 고쳐 쓰기와 파생물

- 차량의 Pleos STT 결과가 1차입니다. 받는 대로 저장합니다.
- 후처리(화자 대조, T38)는 같은 줄의 `profile_id`를 채우고 `revision`을 올립니다. 서버에서 글자를 다시 받아 적지는 않습니다(ADR-0008).
- 부탁, 도착 할 일, 장면 같은 파생물은 발화 줄에 넣지 않습니다. 지금처럼 여행 문서에 두고, 근거가 된 발화의 순번 범위를 적어 다시 만들 수 있게 합니다.
- 후처리는 Postgres의 작업 표에서 한 건씩 꺼내 돌립니다(`FOR UPDATE SKIP LOCKED`). 처음에는 API 프로세스 안에서 돌리고, 무거워지면 워커로 뗍니다. 큐 서비스는 두지 않습니다(T39·T38의 구현은 작업 표 없이 바로 처리함, '결과'의 표).

### 5. 원음 클립

- 원음 전체는 차에 둡니다. 차 밖으로 보내는 범위는 T12(ADR-0007, PR #55)가 '사람이 장면으로 확정한 구간의 클립만'으로 정했습니다. 화자 대조(T38)를 위해 발화 음성이 잠시 서버로 가는 것은 저장하지 않는 별개 경로입니다. 이 절은 클립을 올리는 방법만 정합니다.
- 클립은 차량 앱이 S3 데이터 버킷의 `clips/` 아래에 짧게 서명한 주소로 직접 올립니다. API와 프록시를 거치지 않습니다. DB에는 열쇠와 구간(`audio_ref`)만 둡니다. 내려받을 때는 서명 주소를 주지 않고 `media.gachita.mangowhois.ai`에서 API가 권한을 확인하고 흘려보냅니다([ADR-0020](0020-media-delivery-subdomain.md)).

### 6. 보관

- `utterances`는 여행과 수명이 같습니다. 여행을 지우면 같이 지워지고, 48시간이 지난 여행의 발화는 하루 한 번 지웁니다.
- 사람이 고른 장면은 그때 프로필 DB로 복사합니다.

```sql
CREATE TABLE IF NOT EXISTS moments (
  id          uuid PRIMARY KEY,
  profile_id  uuid NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  trip_code   text NOT NULL,             -- 어느 여행이었는지. 여행 쪽은 지워졌을 수 있음
  started_at  timestamptz NOT NULL,
  ended_at    timestamptz NOT NULL,
  lines       jsonb NOT NULL,            -- 고른 구간의 발화 사본 [{ at, text, profile_id }]
  clip_key    text,                      -- S3 클립. 있을 때만
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS moments_feed ON moments (profile_id, started_at DESC);
```

- 프로필을 지우면 그 사람의 `moments`가 같이 지워집니다. 그룹에서 나가거나 그룹을 지울 때의 처리는 T45와 맞춥니다.

### 7. 하지 않는 것

- 전사를 S3에 통째로 두지 않습니다. `trips.doc`에 넣지 않습니다.
- 검색 색인을 만들지 않습니다. 필요해지면 그때 정합니다.
- 큐 서비스(Kafka, SQS)와 실시간 채널(웹소켓)을 지금은 두지 않습니다.

## 결과

- T39의 할 일 가운데 '발화 저장', '기록본 읽기', '48시간 뒤에 무엇이 남는지'의 모양이 이 결정으로 정해집니다. 표와 API, 명세(`docs/api/`)는 T39에서 만듭니다. 이 문서의 SQL과 요청 모양은 초안입니다.
- **T39의 구현(PR #85, 11/13 기준 병합 전)에서 정해진 이름과 달라진 점.** 표와 API의 기준은 그 PR의 `trips-2-utterances.sql`, `profiles-3-moments.sql`, `docs/api/openapi.yaml`입니다.

  | 이 문서의 초안 | T39의 구현 |
  |---|---|
  | `device_id`, `started_at`·`ended_at` | `device`, `at`(발화 시각 하나, epoch ms) |
  | `seat_zone`(숫자) | `seat_area`(Pleos SeatArea의 이름) |
  | `geo`(jsonb) | `lat`, `lng` |
  | `revision`(고쳐 쓴 횟수) | 없음. 대신 `generation`(동의 세대, T12의 결정): 세대가 바뀌면 옛 세대의 발화를 지움 |
  | `audio_ref`(클립) | 아직 없음. 범위는 '고른 장면만'(T12), 칸은 숏폼(T43) 때 |
  | 외래 키(`REFERENCES trips`), '하루 한 번 지움' | 외래 키 없음. 새 여행을 만들 때 48시간 지난 여행과 그 발화를 지움 |
  | `received_at` | `created_at`(ADR-0016의 발화 신선도 SLI가 씀) |
  | 후처리 작업 표(4절) | 없음. 화자 대조는 음성을 올릴 때 바로(T38, PR #101) |
  | 파생물의 '근거 발화 순번 범위'(4절) | 장면에 없음(`at`만) |
  | 응답 `acked_seq` | `lastSeq` |
  | 한 번에 100줄·256 KB(예) | 500줄·1 MB |
  | `moments`에 발화 사본(`lines`) | `profile_moments`에 장면의 시각·위치·이름표만. 발화 글자는 복사하지 않음 |

  마지막 줄의 차이로, 아래 '정해야 하는 것'의 둘째(다른 사람의 말이 복사돼 남는 문제)는 지금 구현에서는 생기지 않습니다.
- 프로필 DB에 표가 하나 늘지만 길은 그대로입니다. 두 DB에 닿는 것은 여전히 API뿐입니다. 피드는 48시간 안의 발화는 여행 DB에서, 남긴 장면은 프로필 DB에서 따로 읽어 합칩니다(한 질의로 묶지 않음). 48시간 뒤에는 프로필 DB만 읽습니다.
- 인프라에 새로 필요한 것은 없습니다. 클립을 올리게 되면 API의 역할에 `clips/` 접두사의 서명 권한이 필요합니다(고른 장면의 클립, T43).
- **정해야 하는 것(기획과 담당)**
  - 48시간 뒤에 남기는 범위. 이 결정은 기준 문서의 '선택한 장면만 개인 앨범에'를 따랐습니다. 전체 전사나 요약을 남기려면 `moments`의 모양이 달라집니다.
  - 장면에는 여러 사람의 말이 들어갑니다. 한 사람이 고른 장면에 다른 사람의 말이 복사돼 남아도 되는지, 그 사람의 동의를 어떻게 받는지.
  - 목소리 대조에 쓰는 값은 생체 정보로 다뤄질 수 있습니다(T38).
- **확인하지 못한 것**
  - 실제 가족 대화의 발화량과 한 줄의 크기. 위의 양은 합성 음성으로 잰 것입니다.
  - Pleos STT가 발화마다 확신도와 시작·끝 시각을 주는지. 주지 않으면 그 열은 비웁니다.
  - 차량 앱이 통신이 끊긴 동안 보관할 수 있는 양(T36).
  - 조사한 세 제품의 서버 쪽 저장 방식. 클라이언트에서 보이는 것만 읽었습니다.
