# ADR-0006: OAuth 제공자는 구글, 받는 정보는 번호와 이름만

* **상태:** 채택됨, 2026-11-13
* **관련:** T21, #26, ADR-0004

## 배경

기기 프로필은 기기를 바꾸면 이어지지 않는다. 계정으로 프로필을 이어 받으려면 일반 OAuth 제공자가 필요하다(T21). 현대 계정 연동은 제휴 조건 확인 전이라 별도 모듈로 남는다(ADR-0004).

## 검토한 선택

| 제공자 | 받는 점 | 걸리는 점 |
|---|---|---|
| **구글** | 개인 자격으로 클라이언트 등록이 바로 됨. OIDC 표준(토큰 교환·사용자 정보). 시연용 테스트 사용자 100명 | 한국 사용자에게 카카오만큼 익숙지 않음 |
| 카카오 | 한국 사용자에게 가장 익숙 | 서비스 운영은 비즈 앱(사업자) 전환이 필요. 테스트 앱은 등록 멤버로 제한 |
| 네이버 | 개인 등록 가능 | 절차와 문서가 정리돼 있지 않아 확인 비용이 큼 |
| 애플 | - | 유료 개발자 계정 필요 |

## 결정

- 제공자는 **구글** 하나로 시작한다. 개인 자격으로 클라이언트를 만들 수 있어 2차 PT(12/3~4) 전에 실제로 써 볼 수 있는 경로가 가장 짧다. 카카오는 프로필 표와 여행 흐름이 제공자를 모르게 되어 있으므로(아래) 나중에 같은 자리에 추가할 수 있다.
- 받는 정보는 사용자 고유 번호(`sub`)와 이름뿐. 이메일은 받지 않는다 — 쓸 곳이 없어 동의 범위를 넓힐 이유가 없다.
- 구현은 `backend/api/providers/google.js` 한 파일(ADR-0004의 제공자 자리). 서버의 나머지는 제공자 이름만 안다. 의존성은 늘리지 않는다(Node 22 기본 `fetch`). 토큰 교환·사용자 정보 주소와 클라이언트 값(`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`)은 환경 변수로 받고, 테스트는 주소를 가짜 제공자로 바꿔 돈다.
- 클라이언트는 인증 코드만 서버에 넘긴다. 코드→토큰 교환은 서버가 하므로 클라이언트 비밀 값은 클라이언트에 두지 않는다.
- 한 프로필에 제공자 연결은 하나다. 토큰 없이 계정으로 찾아 들어오면 새 기기 토큰을 돌려주고 이전 토큰은 못 쓰게 된다(프로필에 토큰 해시가 하나뿐). 여러 기기가 같은 프로필을 함께 쓰는 모습은 필요해지면 다시 나눈다.

## 결과

- 프로필 표에 `provider`, `provider_user_id` 칸이 들어간다(`profiles-2-links.sql`). 기존 기기 프로필은 빈 값으로 그대로 읽힌다 — 기존 테스트가 통과하는지로 확인한다.
- `docs/api/openapi.yaml`에 `/api/profiles/me/links/google`(POST, DELETE)가 들어가고 프로필 응답에 `links`가 붙는다.
- `docs/api/external.md`의 인증 향은 그대로(Let's Encrypt). 구글 OAuth가 서버가 부르는 첫 외부 API가 되므로 external.md에 향을 더한다.
