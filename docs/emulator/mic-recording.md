# 차량 마이크 원음 녹음 (T10)

2026-11-13에 Pleos Connect Emulator 2.1.0에서 잰 결과입니다. **모든 값은 에뮬레이터에서 본 것이고 실차가 아닙니다.** 근거 표시는 [에뮬레이터 스펙](README.md)과 같습니다(문서 · 에뮬 · 모름).

## 결론: 조건부

일반 앱(우리 앱)은 `AudioRecord`로 차량 마이크의 원음을 녹음할 수 있었습니다. 앞 화면, 기어 D, 음악·TTS 재생 중, 마이크 유형 포그라운드 서비스를 둔 화면 뒤에서 넣은 소리가 그대로 파일에 들어갔고, 내비를 앞에 둔 채 30분 동안 끊기거나 막히지 않았습니다. 녹음하면서 0.1초 조각마다 서버로 바로 보내는 실시간 전송도 됐습니다. **하지만 우리가 녹음하는 동안 Gleo는 듣지 못하고, STT가 마이크를 직접 여는 `request()`도 무음만 받습니다.** 우리 녹음을 STT에 넣는 `sendAudio()`는 함께 쓸 수 있었습니다(별도 시험). 우리 앱이 Gleo를 대신 깨워 마이크를 넘겨주는 길도, 뒤쪽 마이크로 비켜 가는 길도 에뮬레이터에서는 막혔습니다. 그래서 차에서 수음하려면 Gleo와 마이크를 주고받는 흐름이 필요합니다.

## 권고

녹음 위치와 받아쓰기 방식은 ADR-0008(['차량에서 수음하고 Pleos STT로 받아 적는다'](https://github.com/team-pitcrew/gachita/pull/59), PR #59에서 제안)을 따릅니다. 이 문서의 관찰에서 나오는 구현 조건은 다음과 같습니다.

- 수음은 앞 화면에서 시작한 마이크 포그라운드 서비스의 `AudioRecord`로 합니다. 받아쓰기는 STT가 마이크를 여는 `request()`가 아니라, 우리 녹음을 넣는 `sendAudio()`(ON_DEVICE)로 합니다.
- Gleo와는 마이크를 나눠 쓸 수 없습니다. 호출어(우리 전사에서 감지)나 우리 화면의 단추로 수음을 멈춘 뒤 사용자가 운전대 버튼으로 Gleo를 부르고, Gleo가 끝나면 다시 수음합니다. 우리 앱이 Gleo를 대신 깨우는 길은 없습니다.
- 수음 중이라는 것과, 그동안에는 운전대 버튼만 눌러서는 Gleo가 응답하지 않는다는 것을 화면에 보입니다.

## 실시간 전송

녹음하면서 0.1초 조각(16 kHz 모노 3.2 KB)마다 TCP로 Mac의 시험 서버에 바로 보냈습니다. 에뮬레이터에서 Mac은 `10.0.2.2`입니다. 앱 저장소에도 같은 WAV를 써서, 서버가 받은 것과 비교했습니다.

| 조건 | 길이 | 받은 조각 | 서버 사본 | 넣은 음성 | 보낸 뒤 도착까지 | 근거 |
|---|---|---|---|---|---|---|
| 앞 화면, 기어 P | 60초 | 600 / 600 | 기기 파일과 바이트 단위로 같음 | 2 / 2 | 3~8 ms | 에뮬 |
| 화면 뒤(내비가 앞), 서비스 | 120초 | 1200 / 1200 | 같음 | 5 / 5 | 5~17 ms | 에뮬 |
| 기어 D 40 km/h, 화면 뒤(내비가 앞), 서비스 | 10분 | 6000 / 6000 | 같음 | 9 / 9 | 2~20 ms | 에뮬 |

- 조각은 서버에 약 0.1초 간격(가운데 값 102~104 ms, 95%가 111 ms 안, 가장 길 때 192 ms)으로 왔고, 빠진 조각은 없었습니다. 앱에서 한 조각을 보내는 데 걸린 시간은 가장 길 때 15 ms였습니다. 녹음 막힘은 한 번도 없었습니다.
- **지연:** 조각이 0.1초 분량으로 다 찬 뒤 보내므로 조각의 첫 소리는 약 0.1초 늦게 떠납니다. 보낸 뒤 도착까지는 위 표의 값입니다. 에뮬레이터 시계가 Mac보다 약 169 ms 늦어서, adb로 잰 시계 차이(오차 ±5~6 ms)를 빼서 계산했습니다. 소리를 넣은 시각을 기준으로 재려 했지만, 에뮬레이터가 넣은 소리를 실제 시간보다 빨리 받아들여 쓰지 않았습니다.
- 에뮬레이터의 통신은 Mac 안의 가상 연결이라 실차의 LTE, 터널, 음영 구간과 다릅니다(모름). 통신이 끊겼을 때 조각을 모아 두었다 다시 보내는 처리, 압축, 암호화(TLS)는 넣지 않았고 시험하지 않았습니다.
- 실시간 전송도 같은 `AudioRecord`를 쓰므로 Gleo·Pleos STT와의 충돌, 화면 뒤에서 서비스가 필요한 것은 위 녹음 결과와 같습니다.

| `VOICE_RECOGNITION` | 16 kHz 모노, 48 kHz 스테레오 | 들어감 | 없음 |
| `UNPROCESSED` | 16 kHz 모노 | 들어감 | 없음 |
| `CAMCORDER` | 16 kHz 모노 | 들어감 | 없음 |
| `VOICE_COMMUNICATION` | 16 kHz 모노 | 들어감 | 없음 |
| `VOICE_PERFORMANCE` | 16 kHz 모노 | 들어감 | 없음 |
| `MIC` | 8 kHz 모노, 48 kHz 모노, 48 kHz 스테레오 | 들어감 | 없음 |

- 입력 장치는 `Built-In Mic`(유형 15)로 잡혔습니다. 시스템은 내장 마이크 4개(`builtin_mic1`~`4`)를 알렸습니다. 스테레오 녹음의 두 채널은 바이트 단위로 같지 않았지만, 실제로 다른 마이크인지는 확인하지 않았습니다.
- 소스마다 붙은 효과(잡음 제거, 반향 제거) 수는 0으로 보고됐고, 시스템은 `UNPROCESSED` 지원을 `false`로 알렸지만 녹음은 됐습니다. 에뮬레이터에서는 소스에 따른 소리 차이를 볼 수 없습니다. 실차에서는 소스마다 처리가 다를 수 있습니다(모름).

## Gleo와 우리 STT

**Gleo**는 운전석 PTT(`cmd voiceinteraction show`)로 불렀습니다.

- 우리가 녹음하는 동안: Gleo가 PTT를 받았지만 `preProcessSystemEvent() : isUsingPrimaryMic is activated, ignoring`, `startPttButton() is ignored`로 무시했습니다. 녹음이 없을 때는 같은 명령에 `ListeningPassiveState`로 갔습니다(대조군).
- Gleo가 먼저 듣는 중에 우리가 녹음을 시작: Gleo는 계속 서버 STT로 소리를 보냈지만, 1초 묶음의 압축 크기가 음성을 넣는 동안 350~412바이트로 떨어졌습니다. 같은 Gleo가 무음일 때 994~1040바이트, 음성을 들을 때 1834~3661바이트(11/2 기록)였으므로, 이 동안 Gleo는 무음을 받은 것으로 봅니다. Gleo는 아무 말도 알아듣지 못하고 5초 뒤 잠들었고, 같은 시각 우리 파일에는 그 음성이 그대로 있었습니다.
- Gleo가 말하는 동안(우리 화면을 열고 답하는 중) 녹음을 시작: 녹음은 막히지 않았고, Gleo가 말하기 시작하고 1.5초 뒤 넣은 음성이 우리 파일에 그대로(조각 일치 100%) 들어갔습니다. Gleo의 말하기 상태는 6.0초로 끊기지 않았고 스피커 출력에도 약 5초 소리가 있었습니다. Gleo가 '로디, 레벨 설정 열어 줘'를 듣고 말하게 하려면 에뮬레이터를 다시 켠 직후여야 했습니다(아래 '에뮬레이터 충돌').
- 호출어로 부르는 경우와 실제 운전대 PTT 단추는 시험하지 않았습니다.

**우리 Pleos STT**(ON_DEVICE)는 Gleo의 음성 서비스가 우리 앱 이름으로 마이크를 따로 엽니다(`[GAAS]AudioRecorderImpl start(ai.roaddy.featureprobe)`). 우리 `AudioRecord`가 열려 있는 동안 STT는 소리 크기 알림이 오지 않았고 받아 적은 말이 없었습니다. 녹음이 끝나자 바로 소리 크기 알림(약 4.5)이 다시 왔습니다. 녹음 먼저·STT 먼저 두 순서 모두 같았습니다. STT 단독으로는 받아 적기가 된 것을 11/2에 확인했습니다. STT가 마이크를 직접 여는 대신 우리 앱이 연 원음을 `sendAudio()`로 넣는 길은 우리 녹음과 함께 11분 동안 받아 적었다는 별도 시험이 있습니다(`research/evidence/20261113-stt-longform/`, 저장소 밖). 이 경우에도 우리 앱이 마이크를 잡으므로 Gleo 문제는 그대로입니다.

### 우리 앱이 Gleo에 마이크를 넘겨줄 수 있나

우리 앱이 수음하다가, 사용자가 Gleo를 원하면 마이크를 놓고 Gleo를 깨운 뒤 끝나면 다시 수음하는 흐름과, 다른 마이크를 쓰는 방법을 시험했습니다.

| 시도 | 결과 | 근거 |
|---|---|---|
| 앱이 Android 표준 비서 호출(`startActivity(ACTION_ASSIST)`) | Gleo 화면(`MainActivity`)이 떴다가 약 50 ms 만에 닫히고 듣기 상태로 가지 않음. 녹음 중에도, 녹음을 놓은 뒤에도 같음 | 에뮬 |
| 앱이 쓸 수 있는 다른 Gleo 호출 길 | 문서에 없음. Gleo가 받는 인텐트에도 없음(설정·기록 화면, TTS 멈춤뿐) | 문서, 에뮬 |
| 우리 녹음을 뒤쪽 마이크(`Built-In Back Mic`)로 지정 | 실제로 뒤쪽 마이크로 녹음됐지만 Gleo는 `isUsingPrimaryMic: true`로 PTT를 무시함. Gleo가 먼저 듣고 있었을 때도 Gleo가 무음을 받아 잠듦 | 에뮬 |
| 우리 녹음을 놓은 뒤 사용자가 직접 PTT | Gleo가 들음(위의 대조와 같음) | 에뮬 |

- 에뮬레이터에서는 두 마이크가 같은 입력 통로(`primary input`) 아래에 있었습니다. 실차의 마이크 구성은 다를 수 있습니다(모름).
- 그래서 남는 흐름은 '우리 앱이 먼저 마이크를 놓고, 사용자가 운전대 버튼으로 Gleo를 부르는' 두 단계입니다. 운전대 버튼을 먼저 누르면 Gleo가 무시하고 우리 앱에 알리지 않으므로 이 순서를 바꿀 수 없습니다.
- 마이크를 놓는 계기와 다시 수음하는 부분은 다른 세션이 쟀습니다(`research/evidence/20261113-gachita-e2e/`, 저장소 밖). 우리 전사에서 호출어("글레오", 받아 적힌 글자는 "클레오")를 알아채 수음을 멈추자 PTT가 받아들여졌고, Gleo가 잠든 뒤 오디오 포커스가 돌아온 것을 보고 PTT 6.1초 뒤 다시 수음했습니다(에뮬). 문서도 Gleo가 불리면 오디오 포커스를 가진 앱이 `AUDIOFOCUS_LOSS_TRANSIENT`를 받는다고 적었습니다(문서).

Pleos 공식 문서에 적힌 차량 마이크 경로는 SpeechToText의 `request()`뿐이고, 이 경로는 앱에 원음을 주지 않고 글자와 소리 크기만 줍니다(문서). 문서는 앱이 차량 하드웨어에 직접 접근하지 말고 SDK의 표준 API를 쓰라고 적었습니다. Android의 `AudioRecord`가 여기에 어긋나는지는 문서에서 찾지 못했습니다(모름).

## 자원

에뮬레이터의 vCPU 4개 중 한 코어 기준 사용률이고 참고값입니다. 실차의 칩은 모릅니다.

| 조건 | 우리 프로세스 CPU | 메모리(PSS) |
|---|---|---|
| 10~30초 녹음 21회(조건 1~5) | 한 코어의 0.3~2.2% | 42~53 MB |
| 30분 녹음(조건 6) | 한 코어의 0.57%(1분 단위 0.51~2.17%) | 50.4~51.5 MB, 30분 동안 늘지 않음 |
| 녹음하며 실시간 전송(1~10분) | 한 코어의 0.8~1.9% | 46~51 MB |

Pleos 기준은 주행 중 내비가 아닌 앱 CPU 5% 미만, RAM 400 MB 이하입니다(문서). 16 kHz 모노 16비트 원음은 1분에 1.9 MB, 1시간에 115 MB입니다.

## 확인하지 못한 것

- **실차.** 실제 마이크 배열, 잡음 제거·반향 제거, 스피커 소리가 마이크로 다시 들어오는 정도. 에뮬레이터에서는 스피커 출력이 가상 마이크로 들어가지 않아, 음악과 TTS가 녹음에 섞이는지 볼 수 없습니다.
- 사람 목소리와 차 안 소음. 넣은 음성은 macOS 합성 음성(Yuna)입니다.
- 44.1 kHz(위 표), Gleo 호출어, 실제 PTT 단추, 다른 앱(예: 통화)이 마이크를 쓸 때.
- 화면이 꺼지거나 차가 꺼질 때, 앱이 시스템에 의해 끝날 때 녹음 파일이 어떻게 남는지.
- 화면 뒤에서 포그라운드 서비스를 시작할 때의 정확한 유예 시간. 같은 순서로 두 번 보내 한 번 성공, 한 번 실패였습니다.

## 에뮬레이터 충돌

소리 넣기(gRPC `injectAudio`)를 시작할 때 에뮬레이터가 두 번 멈췄습니다(00:40, 00:50). 두 번 모두 SIGSEGV이고, 스택 맨 위가 `audio_forwarder_enable` ← `QemuAudioInputEngine::start` ← `EmulatorControllerImpl::injectAudio`로 11/2의 세 번과 같습니다. 두 번째는 Gleo만 마이크를 열고 있을 때였고, 첫 번째는 화면 뒤에서 포그라운드 서비스를 시작한 직후였습니다(그 회차의 앱 기록은 충돌로 잃음). 우리 `AudioRecord`가 열려 있는 동안 넣은 소리 80번에서는 한 번도 멈추지 않았습니다. 원인은 확인하지 않았습니다. Gleo만 마이크를 열고 있을 때 넣는 것은, 다시 켠 뒤 우리 앱이 아직 수음하지 않은 부팅에서는 두 번 모두 됐습니다. 같은 부팅에서 우리 앱이 먼저 수음했다가 멈춘 뒤에는 첫 소리 넣기도 멈췄습니다(다른 세션 05:57, 06:04).

## T12가 이어받을 때

- 원음을 어디서 녹음하든, 같은 기기에서 음성 비서나 다른 음성 입력과 마이크를 나눠 쓸 수 없다고 보고 설계합니다. 에뮬레이터에서는 누가 먼저 열었든 우리 쪽(앞 화면에 있거나 포그라운드 서비스를 둔 일반 앱의 `AudioRecord`)이 소리를 가져갔고, Gleo와 Pleos STT의 `request()`는 무음을 받거나 듣기를 시작하지 않았습니다.
- 막힘은 오류로 오지 않습니다. 파일이 0으로 채워지다가 `read()`가 돌아오지 않게 됩니다. 녹음 앱은 `AudioRecordingCallback`의 `isClientSilenced`와 0인 구간을 함께 보고, 시간은 샘플 수가 아니라 시계로 적습니다.
- 마이크 포그라운드 서비스는 앱이 앞에 있을 때 시작해야 합니다. 화면 뒤에서 다시 시작할 수 없으니, 끊겼을 때 사용자에게 앱을 열어 달라고 해야 합니다.
- 원음을 실시간으로 서버에 보내는 구조도 기기 쪽에서는 됩니다. 16 kHz 모노 원음은 초당 32 KB(256 kbps)이므로, 주행 중 통신이 끊길 때를 대비해 기기에 모아 두었다 다시 보내는 처리와 압축이 필요합니다.
- 화자 구분·발화자 식별은 Pleos SDK에 없습니다. SpeechToText는 글자, 말의 시작·끝, 소리 크기만 주고 누가 말했는지나 좌석은 주지 않습니다(문서). Gleo는 내부 로그에 좌석 위치(`wwdPosition = ROW_1_LEFT`)를 남겼지만 앱이 받는 길은 문서에 없습니다(에뮬). 온보딩에서 목소리를 등록해 식별하려면 우리 모델이 원음 스트림에서 직접 해야 합니다. 이 문서에서는 시험하지 않았습니다.
- 받아쓰기·화자 구분용으로는 16 kHz 모노 16비트로 충분히 녹음됐습니다. 화자 구분에 다채널이 필요하면 실차의 채널 구성을 따로 확인해야 합니다.
- 폰 수음은 ADR-0008에서 차선안입니다. 쓰게 되면 같은 질문(화면 뒤, 화면 꺼짐, 통화·내비 음성과의 충돌, 길이)을 대표 폰에서 확인해야 합니다. 이번에는 폰을 시험하지 않았습니다.

## 시험 방법과 근거

- **앱:** 프로브 앱 `ai.roaddy.featureprobe`(사용자 10)에 녹음 명령을 더했습니다. `rec:start:<이름>:<초>:<소스>[:<표본율>[:<채널>]]`은 앱에서 바로, `rec:fg:…`는 마이크 유형 포그라운드 서비스 안에서 `AudioRecord`로 녹음해 앱 저장소에 WAV로 씁니다. 5초마다 소리 크기와 0인 비율, 프로세스 중요도를 남깁니다. 프로브 앱은 이 저장소 밖(`tools/feature-probe`)에 있습니다.
- **소리:** 음성 파일을 에뮬레이터의 gRPC `injectAudio`로 가상 마이크에 넣었습니다. 호스트 마이크는 쓰지 않았습니다. 에뮬레이터는 `-grpc 8556 -grpc-use-token -audio none`을 더해 Cold boot로 켰습니다.
- **실시간 전송:** 녹음 명령 끝에 `:<호스트>:<포트>`를 붙이면 조각마다 [보낸 시각, 순번, 길이] 머리와 PCM을 TCP로 보냅니다. Mac의 시험 서버가 받은 시각과 순번을 남기고 WAV로 저장합니다.
- **판정:** 넣은 음성의 0.25초 조각을 녹음 파일에서 찾는 스크립트로 확인했습니다. 녹음 파일, 로그 발췌, `results.json`, 다시 돌리는 스크립트는 저장소 밖 증거 폴더 `research/evidence/20261113-mic-recording/`에 있습니다. 녹음 파일과 원본 로그는 저장소에 넣지 않습니다.
