# 확장 API 여정을 확인하는 법

기본 `make e2e`의 12단계와 별도로, T38·T43·T75·T76가 이어지는지를 실제 HTTP로 확인합니다. 서버가 클립 저장소나 재전사를 갖추지 않았으면 전체 성공으로 표시하지 않습니다. 이 검사는 배포 완료 판단을 돕는 도구이며 폰·차 화면 전체 검증을 대신하지 않습니다.

## 로컬에서 같은 흐름 재현

Node 22, Docker, 검사할 서버의 `npm ci`가 필요합니다. 다른 세션의 개발 Postgres를 쓰지 않고, 컨테이너 이름과 포트를 매번 새로 잡습니다.

```sh
cd backend/api && npm ci && cd ../..
node .github/scripts/journey-local.mjs . ready
node .github/scripts/journey-local.mjs . asr-disabled
node .github/scripts/journey-local.mjs . asr-missing
node .github/scripts/journey-local.mjs . storage-missing
```

- `ready`: 실제 서버 모듈·Postgres와 **가짜 S3/ASR HTTP 서버**를 연결합니다. 저장소·ASR 함수 자체를 가짜로 바꾸지 않고, 운영 코드가 쓰는 SDK/HTTP 경로를 통과합니다. 인증·클립·후보·자막·삭제가 이어지고 저장소 객체가 0개가 됐는지 확인합니다. 이어 같은 임시 DB에서 새 시험 여행 한 줄의 생성 시각만 49시간 전으로 바꾸고 만료 치우기를 불러 여행 404·클립 행/바이트 0·선택한 앨범 복사본 보존을 확인합니다. 실제로 48시간을 기다리거나 공용 시계를 바꾸는 시험은 아닙니다.
- `asr-disabled`: ASR 설정을 뺀 채 나머지 연결과 원문 자막을 확인하고 `partial`을 남깁니다. 실제 외부 호출이 0회인지 확인합니다.
- `asr-missing`: ASR 설정을 빼면 확장 검사 결과가 `failed`가 되는지 확인합니다. 원문으로 보이는 것을 재전사 성공으로 세지 않습니다.
- `storage-missing`: 클립 버킷 설정이 없을 때 업로드와 정리 DELETE의 503을 모두 실패로 보고하는지 확인합니다. 이 경우도 로컬 DB의 활성 클립·발화·프로필·토큰·목소리·앨범과 저장소 객체가 0개인지 별도로 확인합니다.
- 뒤 두 명령의 종료 코드 0은 **예상한 실패를 확인했다**는 뜻입니다. 출력에는 `status: failed`와 `fixture.expectedFailure: true`가 함께 남습니다.
- 임시 DB 컨테이너는 성공·실패 모두 제거합니다. AWS/ASR 자격은 로컬 대역용 값이며 외부 서비스를 호출하지 않습니다.

첫 인자는 검사할 checkout 경로입니다. 여러 PR을 합친 별도 checkout을 지정할 수 있습니다. 이때 스크립트가 있는 checkout과 서버 checkout의 커밋을 검증 기록에 함께 적습니다. 필요한 API가 아직 없는 develop에서 실패하는 것은 정상적인 준비 상태 실패이며, 검사를 약하게 바꿀 이유가 아닙니다.

## 배포된 서버 확인

실제 환경에 시험 데이터를 만들어도 되는 때에 실행합니다. `.github/workflows/journey-e2e.yml`의 수동 실행도 같은 명령이며 대상 주소와 시험 데이터 생성 확인(`confirm`)을 명시해야 합니다. 기존 `live-e2e`와 자동 배포 검사는 바꾸지 않습니다.

```sh
node .github/scripts/journey-e2e.mjs https://대상주소 \
  --storage=s3 --asr=required > journey-result.json
```

`--asr=required`는 제한 시간 안에 실제 `asrText`가 생기고 숏폼 자막이 원문과 함께 제공돼야 합니다. 설정이 없거나 연결이 실패해 원문으로 남으면 종료 코드 1입니다. ASR를 일부러 끄고 나머지 경로만 확인하려면 `--asr=unverified`를 씁니다. 이때 결과는 `partial`, 종료 코드는 3이며, 전체 검증 성공으로 쓰지 않습니다.

기본 클립과 목소리 등록은 합성 파형입니다. 이는 오디오 처리·등록·대조·반환 계약을 확인하며 한국어 인식 품질을 검증하지 않습니다. `--wav=<25초_16kHz_모노_PCM_WAV>`로 클립을 바꿀 수 있지만 시험의 글·시각은 고정돼 있으므로, 실제 가족 대화 정확도는 별도 정답 대본으로 측정해야 합니다. 합성 파형을 말소리 없음으로 처리하는 실제 ASR에서는 결과가 생기지 않아 `required` 검사가 실패할 수 있습니다. 실패만으로 미설정과 무음 판정을 구분할 수는 없습니다.

`--storage=s3`는 실행자가 지정한 환경 설명입니다. HTTP로 동일한 클립 바이트를 돌려받는 것은 확인하지만, 버킷 설정·역할·버전 관리를 직접 감사한 것은 아닙니다. T64의 실제 파드 시험과 `list-object-versions` 증거를 함께 남겨야 합니다.

## 확인하는 연결과 정리

1. 두 프로필·참가자를 만들고 자기 토큰만 동의 ON을 허용하는지 봅니다.
2. 발화를 올리고 중복 전송·다른 참가자의 기기 토큰을 확인합니다.
3. 목소리 등록과 대조로 화자를 붙인 뒤 개인 피드가 다른 사람의 발화를 섞지 않는지 확인합니다.
4. 추천 후보를 선택해 장면으로 저장하고 고른 사람의 앨범에만 들어가는지 확인합니다.
5. 클립을 올리고 같은 바이트를 인증된 요청으로 받습니다. 숏폼의 화자·자막 시각·클립 주소를 확인합니다.
6. 재전사 결과와 Pleos 원문이 함께 남는지 봅니다.
7. 자기 글과 클립 삭제, 지운 클립의 재업로드 차단을 확인합니다.
8. 동의를 끄면 기록이 멈추고 글·클립에 더 접근할 수 없으며 옛 세대 업로드가 거절되는지 봅니다.

실패해도 `finally`에서 만든 클립 삭제, 동의 OFF, 여행 종료, 프로필 삭제를 시도합니다. 정리 실패는 결과에 남고 전체 실패가 됩니다. 여행 DELETE API가 없어서 원격 실행의 빈 시험 여행과 장면 메타데이터는 남습니다. 제목은 `E2E 확장 여정`이며 결과의 `cleanup.retainedTrips`에 제목·개수를 남깁니다(접근 가능한 여행 코드와 토큰은 출력하지 않습니다). 운영 `ops clean-e2e` 또는 48시간 만료로 정리합니다. 결과에는 프로필·참가자 토큰이나 요청/응답 본문을 출력하지 않습니다.
